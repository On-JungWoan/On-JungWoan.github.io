# 개발 블로그 유지보수

## 1. 작업 위치를 정한다

요청과 가장 가까운 기존 구현 하나를 먼저 읽고 수정 범위를 좁힌다.

- 포트폴리오: `index.html`, `assets/css/academic.css`, `assets/images/`
- 블로그 글: `_posts/`, 관련 `_layouts/`와 `_includes/`
- 탐색·사이트 설정: `_data/navigation.yml`, `_config.yml`
- 연구 페이지: `projects/<slug>/index.html`, `assets/paper/`

## 2. 콘텐츠를 다룬다

- 사용자가 제공하지 않은 개인 이력, 연구 성과, 논문 게재 상태, 수치, 링크를 만들지 않는다.
- 대상 페이지의 언어와 문체를 유지하되 사용자의 명시적 요청을 우선한다.
- 새 글은 `_posts/<분류>/YYYY-MM-DD-slug.md`에 만들고 유사한 최신 글의 frontmatter를 복제해 필요한 값만 갱신한다.
- `date`와 `last_modified_at`을 실제 변경일에 맞추고, 수식이 있을 때만 `use_math: true`를 사용한다.
- 새 이미지는 의미가 드러나는 파일명으로 저장하고 본문에 대체 텍스트를 작성한다.

## 3. 화면을 수정한다

- 기존의 절제된 학술 포트폴리오 시각 언어와 색상·간격을 우선 재사용한다.
- `index.html`과 독립형 프로젝트 페이지의 스타일은 해당 페이지 범위에 한정해 다른 블로그 화면에 영향을 주지 않게 한다.
- 새 라이브러리나 CDN을 추가하기 전에 기존 HTML, CSS, JavaScript로 해결 가능한지 확인한다.
- 360px 안팎의 모바일 폭부터 데스크톱까지 내용이 잘리거나 겹치지 않게 한다.
- 링크와 컨트롤에 키보드 포커스를 제공한다.
- 생성된 번들·압축 파일은 직접 고치지 말고 원본 또는 빌드 절차를 수정한다.

## 4. 결과를 확인한다

1. 변경한 링크, 이미지 경로, Liquid 표현식, frontmatter를 다시 확인한다.
2. 화면 변경이면 가능한 환경에서 데스크톱과 모바일 미리보기를 확인한다.
3. `git diff --check`와 `git status --short`로 요청 밖의 변경이 없는지 확인한다.

검증 실패는 숨기지 말고 새 변경의 문제인지 기존 환경의 문제인지 구분해 보고한다.
