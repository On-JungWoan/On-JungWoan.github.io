# 개발 블로그 리팩터링

## 1. 작업 성격을 구분한다

- 진단·검토 요청이면 파일을 바꾸지 말고 근거와 우선순위가 있는 보고서를 작성한다.
- 수정 요청이면 진단 결과를 작은 단계로 나누고 검증 가능한 단위부터 구현한다.
- 전체 리팩터링이면 단계별 계획을 세우고 각 단계가 통과한 뒤 다음 단계로 진행한다.
- 디자인 개편, 콘텐츠 교정, 프레임워크 교체, 의존성 업그레이드는 명시적으로 요청된 경우만 포함한다.

## 2. 변경 전 기준선을 만든다

1. `git status --short`로 기존 변경을 확인하고 사용자 작업을 덮어쓰지 않는다.
2. `bundle exec jekyll build`를 실행해 기존 오류와 경고를 기록한다.
3. `/`, `/blog`, 게시물, `projects/*` 등 영향받는 공개 경로와 소스 파일을 연결한다.
4. `rg --files`, `rg`, 파일 크기와 참조 관계로 중복·결합·미사용 후보를 찾는다.
5. 화면이 바뀔 수 있으면 가능한 환경에서 데스크톱과 모바일 기준 화면을 확인한다.

정적 검색 결과만으로 코드를 미사용으로 단정하지 않는다. Liquid include, 동적 URL, JavaScript DOM 선택자, CSS 클래스처럼 런타임에 연결되는 참조를 함께 확인한다.

## 3. 우선순위를 정한다

다음 순서로 작업 후보를 정렬하고, 효과와 회귀 위험을 함께 설명한다.

1. 빌드 오류, 깨진 경로, 명백한 버그
2. 안전하게 제거 가능한 중복과 미사용 코드
3. 지나치게 큰 파일과 강한 결합을 줄이는 구조 개선
4. 설정·의존성·빌드 과정 정리
5. 성능과 접근성 개선

측정 가능한 문제를 먼저 고치고, 한 번만 쓰이는 코드를 성급하게 추상화하지 않는다.

## 4. 동작을 보존하며 수정한다

- 공개 URL, permalink, frontmatter, SEO 메타데이터, 분석·댓글, 피드와 사이트맵 동작을 유지한다.
- HTML·Liquid 추출 시 데이터 범위와 include 인자를 보존한다.
- CSS 분리 시 cascade, specificity, 선언 순서를 확인하고 전역 선택자 충돌을 만들지 않는다.
- JavaScript 분리 시 로드 순서와 기존 DOM hook을 보존하고 생성 파일이 아닌 원본을 수정한다.
- 공통화는 실제로 반복되는 책임 단위에만 적용하고, 파일을 나누는 것 자체를 목표로 삼지 않는다.
- 제거 전에는 경로, 파일명, selector, include, 설정과 런타임 참조를 검색하고 빌드·화면으로 확인한다.
- 사용 여부가 불확실한 항목은 삭제하지 말고 후보와 확인 방법을 보고한다.

`_site/`, 압축·vendor 파일, `projects/multi-thumbs/viewer/viser-client/assets/`의 해시 번들은 직접 수정하지 않는다. `old/`, 게시물, 대용량 바이너리 자료는 역사적 기록일 수 있으므로 명시적 승인 없이 삭제하지 않는다.

## 5. 작은 단위로 검증한다

각 변경 묶음마다 다음 절차를 반복한다.

1. 하나의 구조적 문제만 수정한다.
2. `bundle exec jekyll build`로 새 오류가 없는지 확인한다.
3. 화면 변경이면 영향받는 경로를 데스크톱과 모바일 폭에서 비교한다.
4. 링크, 이미지, 브라우저 콘솔과 네트워크 오류를 확인한다.
5. `git diff --check`와 `git status --short`로 변경 범위를 검토한다.

JavaScript 원본을 바꾼 경우에만 `npm run build:js`를 실행한다. 기준선에 있던 경고와 새 경고를 구분하고, 회귀가 생기면 다음 단계로 넘어가지 않는다.

## 6. 결과를 기록한다

- 바꾼 구조와 이유를 파일 단위로 요약한다.
- 실행한 검증과 결과를 적는다.
- 보류한 기술 부채와 다음으로 안전한 작업을 우선순위대로 남긴다.
- 제거한 항목은 미사용이라고 판단한 근거를 함께 남긴다.
